# Interview Framework and Process

How to structure and drive a system design interview from the first question to the wrap-up. The framework matters because interviewers evaluate your process as much as your design — a solid architecture presented chaotically scores worse than a simpler one presented clearly.

## Key Points

- **Four-step framework** — clarify requirements (3–5 min), propose high-level design (10–15 min), deep dive into hard components (15–20 min), wrap up with failure modes and extensions (3–5 min). Drive the structure yourself; don't wait for the interviewer.
- **Functional vs. non-functional requirements** — functional is what the system does (features); non-functional is how well (latency, availability, durability). Both must be gathered before drawing anything.
- **Back-of-the-envelope estimation** — quick math using QPS, storage, and bandwidth to determine whether you need one server or a thousand. The goal is order-of-magnitude, not precision.
- **Trade-off articulation** — every design choice has a cost. Naming the trade-off explicitly (e.g., "we're choosing availability over strong consistency") earns more credit than hiding it.
- **Working backwards** — start from user needs → API contract → services → data model → technology choices, not the other way around.
- **API contract definition** — sketch the key endpoints early to force concrete thinking about the user-facing interface, pagination, and data shape.
- **Scope management** — you can't design everything in 45 minutes. Explicitly defer non-critical components and go deep on one or two hard problems.
- **Wrap-up checklist** — proactively identify single points of failure, bottlenecks, monitoring gaps, security concerns, and cost issues in your own design.

## Example

A condensed walkthrough of the first 5 minutes for "Design a URL shortener":

```text
Step 1: Clarify requirements
  Q: "Should we support custom short URLs or only generated ones?"
  A: Both — generated by default, optional custom alias.

  Q: "What's the expected scale?"
  A: 100M new URLs/month, 10:1 read-to-write ratio.

  Q: "Do URLs expire?"
  A: Default TTL of 5 years, configurable.

Step 2: Quick estimation
  Writes: 100M/month ≈ ~40 QPS avg, ~200 QPS peak
  Reads:  ~400 QPS avg, ~2000 QPS peak
  Storage: 100M × 500 bytes ≈ 50 GB/month ≈ 3 TB over 5 years
  → Fits in a single well-provisioned database, but reads benefit from caching.

Step 3: API contract
  POST /urls   { "long_url": "...", "custom_alias": "abc" } → 201 { "short_url": "..." }
  GET  /:code  → 301 redirect to long_url

Step 4: Now draw the high-level architecture...
```

This takes under 5 minutes and gives you and the interviewer a shared foundation before any boxes appear on the whiteboard.
